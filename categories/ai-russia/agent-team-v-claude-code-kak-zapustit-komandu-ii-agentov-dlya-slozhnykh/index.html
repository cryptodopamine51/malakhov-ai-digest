Agent Team в Claude Code: как запустить команду ИИ-агентов для сложных задач

Подготовлено редакцией Malakhov AI

Habr AI·13 июн.·3 минРоссияКод

Claude Code версии 2.1.32 получил экспериментальный режим Agent Team, в котором вместо одного агента задачу разбирает команда: lead-агент координирует работу, а тиммейты работают в параллельных сессиях и переписываются между собой. Режим решает проблему переполнения контекста, когда одна сессия вынуждена одновременно анализировать безопасность, тесты, производительность и архитектуру.

Кратко

  • —Режим включается переменной окружения CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1, нужна версия 2.1.32+.
  • —Тиммейты — отдельные сессии с общим task list; в отличие от субагентов, они общаются друг с другом напрямую.
  • —Два режима отображения: in-process (один терминал, удобно на VPS) и split panes через tmux или iTerm2.
  • —Режим эффективен для code review с разных сторон, поиска багов по нескольким гипотезам и архитектурных споров.
  • —Для мелких правок и последовательных задач режим не подходит: координация съедает больше токенов, чем даёт выигрыш.
Глоссарий · 6 терминов▾
Agent Team
Экспериментальный режим Claude Code, в котором задачу выполняет группа агентов: один координирует (lead), остальные работают параллельно в отдельных сессиях (тиммейты).
Субагент
Вспомогательный агент, запускаемый внутри основной сессии Claude Code для выполнения подзадачи; с другими субагентами не общается.
Task list
Общий список задач, который видят все тиммейты в режиме Agent Team и из которого они самостоятельно берут работу.
Split panes
Режим отображения, при котором каждый тиммейт открывается в отдельной панели терминального мультиплексора tmux или iTerm2.
In-process
Режим отображения Agent Team, при котором все тиммейты работают в одном терминальном окне без внешних зависимостей.
Plan approval
Механизм подтверждения плана действий агента перед тем, как он начнёт редактировать файлы; по умолчанию в Agent Team планы одобряет lead автономно.

Claude Code давно умеет читать проект, редактировать файлы и гонять тесты. Ограничение классического режима — один контекст на сессию: когда задача требует одновременного анализа безопасности, производительности, тестов и архитектуры, агент начинает скакать между темами, теряя детали. Именно для таких случаев в версии 2.1.32 появился экспериментальный режим Agent Team.

В режиме команды одна сессия становится team lead — она координирует работу, ведёт общий список задач и собирает итог. Остальные участники — тиммейты, каждый со своим контекстом. Ключевое отличие от уже существующих субагентов (/agents): тиммейты работают в отдельных сессиях, видят общий task list и могут переписываться между собой, а не просто отчитываться наверх. Субагент работает внутри основной сессии и с другими субагентами не общается — это принципиальная разница в архитектуре.

Для активации нужно установить переменную окружения CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 или прописать её в ~/.claude/settings.json. Отдельной команды для создания команды нет — состав задаётся обычным промптом, где указываются количество тиммейтов и их роли. Claude не создаёт команду без явного запроса или подтверждения пользователя.

Доступны два режима отображения. In-process запускается флагом --teammate-mode in-process: все тиммейты работают в одном терминале, переключение между ними через Shift+Down, просмотр общего task list — Ctrl+T. Этот режим подходит для работы на VPS и по SSH. Split panes (--teammate-mode tmux) открывает каждого тиммейта в отдельной панели tmux или iTerm2 — удобно на локальной машине с большим экраном. По умолчанию режим auto: если среда поддерживает панели, используются они.

Практически режим оправдывает себя в трёх сценариях. Code review с разделением ролей: один агент смотрит безопасность, второй — производительность, третий — тесты, lead сводит находки в приоритизированный список. Поиск сложного бага: несколько тиммейтов параллельно копают разные гипотезы — фронтенд, API, база данных, сессии, гонки — не пересекаясь. Архитектурный спор: агенты проверяют аргументы друг друга при выборе между REST и gRPC или монолитом и микросервисами. Ценность здесь не в параллельности как таковой, а в том, что аргументы проходят взаимную проверку.

Есть и ограничения. Для мелких правок режим избыточен: координация между агентами потребляет больше токенов, чем стоит сама задача. Работа в одном файле грозит конфликтами — зоны ответственности лучше разносить по директориям заранее. Строго последовательные задачи вроде «сначала миграция, потом API, потом фронт» параллелить просто нечего.

Отдельного внимания требует управление промптом. Расплывчатый запрос «улучши проект» приводит к хаосу. Рабочий подход — сразу задать количество тиммейтов, их роли, ограничения на редактирование файлов и формат итога. Авторы рекомендуют добавлять явное требование показать план до начала работы: по умолчанию планы тиммейтов одобряет lead автономно, и без контроля пять агентов могут одновременно внести конфликтующие правки. По завершении работы команду нужно явно закрыть — активные тиммейты остаются живыми сессиями и продолжают потреблять токены.
